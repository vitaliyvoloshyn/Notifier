# Модуль нагадувань

## Моделі

- `Reminder` — правило нагадування, автор, розклад, часовий пояс та політика інформування контролерів.
- `ReminderParticipant` — ролі `controller` та `assignee` в межах конкретного нагадування. Автор є контролером автоматично і не дублюється в цій таблиці. Одна людина може мати обидві ролі.
- `ReminderOccurrence` — окреме заплановане спрацювання правила.
- `ReminderResponse` — незалежний стан відповіді конкретного підлеглого на конкретне спрацювання.
- `ReminderResponseEvent` — журнал відправлень, виконання, відхилень, відтермінувань, завершення часу очікування та помилок доставки.

## Сервісний шар

`reminders.services.create_reminder(...)` створює правило, перше спрацювання, учасників та окрему `ReminderResponse` для кожного виконавця. Якщо виконавців не передано, відповідь створюється для автора. Автор автоматично вважається контролером і не додається повторно як учасник-контролер.

`reminders.services.calculate_next_occurrence(reminder, after=None)` обчислює наступну дату. Для одноразового нагадування повертає `None`; для повторюваного — наступний aware datetime. Якщо `after` не передано, базою є перше спрацювання.

Для місячних і річних повторень зберігається початковий календарний день: 31 січня -> 28 лютого -> 31 березня; 29 лютого -> 28 лютого у невисокосні роки, а потім знову 29 лютого у високосний рік.

## Час і часові пояси

Django працює з `USE_TZ = True`; моменти часу зберігаються в UTC. `TelegramUser.timezone` задає типовий IANA-часовий пояс користувача для нових нагадувань. `Reminder.timezone` фіксує часовий пояс автора на момент створення розкладу, тому подальша зміна налаштування користувача не змінює існуючі нагадування.

Naive datetime, переданий у `create_reminder`, трактується як локальний час у вибраному часовому поясі. Якщо цей час не існує через весняний перехід на літній час, створення відхиляється з `ValidationError`. Неоднозначний час під час осіннього переходу трактується як перше входження (`fold=0`). Автоматично обчислене повторення, що потрапляє в неіснуючу локальну годину, пересувається вперед до першої існуючої хвилини.

Повторення обчислюються за локальним календарем у `Reminder.timezone`, а не додаванням фіксованої кількості секунд. Результат повертається як aware datetime в UTC.

## Відповіді та відтермінування

Відтермінування не є фінальним статусом відповіді: `ReminderResponse.status` залишається `pending`, `deferred_until` зберігає час повторної відправки, а `ReminderResponseEvent` фіксує кожне відтермінування. Після повторної успішної доставки сервіс має оновити `last_sent_at` і `deadline_at`.

Таймер відповіді має запускатися після успішної доставки повідомлення конкретному підлеглому. На час відтермінування старий `deadline_at` потрібно очистити; новий дедлайн встановлюється після повторної доставки.

## Особисті нагадування

Якщо для нагадування не додано жодного учасника з роллю `assignee`, сервіс створює персональну `ReminderResponse` для автора.

## Контроль доступу

Підлеглий може читати тільки власні `ReminderResponse` та пов'язані `ReminderResponseEvent`. Автор і додаткові контролери можуть переглядати відповіді в межах конкретного нагадування. Ці правила мають перевірятися в сервісному/API шарі для кожного запиту, а не лише інтерфейсом Telegram.

## Планувальник доставки

Запуск окремим процесом:

```bash
poetry run python manage.py run_scheduler
```

Планувальник перевіряє настання спрацювань кожні 15 секунд. Для одноразового циклу перевірки можна використати `--once`; інтервал та розмір пакета налаштовуються через `--interval` і `--batch-size`.

Для кожного виконавця надсилається окреме повідомлення. Після успішної доставки записуються `last_sent_at`, `deadline_at`, `telegram_message_id` і подія `notified`. Помилки записуються як `delivery_failed`; невдалі доставки повторюються наступними циклами, тоді як уже успішно доставлені повідомлення не надсилаються повторно. Час у повідомленні показується в часовому поясі конкретного нагадування.

Після успішної доставки всім адресатам поточне спрацювання позначається завершеним, а для повторюваного нагадування створюється наступне спрацювання з індивідуальними відповідями. Одноразове нагадування не отримує наступної дати.

Запускайте один екземпляр `run_scheduler` для одного бота. Захоплення спрацювань використовує транзакцію та `select_for_update`; SQLite не забезпечує повноцінного блокування рядків, тому для кількох паралельних воркерів потрібна БД з підтримкою row-level locks (наприклад PostgreSQL). Завислі записи `processing` старші за 10 хвилин повертаються в обробку. Як і в більшості інтеграцій із зовнішнім API, аварійне завершення між успішною відправкою Telegram і записом результату в БД може спричинити повторну доставку; гарантовано exactly-once доставка тут не заявляється.

Планувальник поки відповідає лише за доставку та створення наступного спрацювання. Обробники Telegram-кнопок, відтермінування та контроль дедлайнів будуть окремим наступним етапом.
